# Длинные Claw-сессии в одном Kimi-чате

## Цель

Один workspace Claw должен продолжать один upstream-чат Kimi во время длинной
задачи. Новый чат допустим только при явном сбросе, другом workspace/session
marker, действительно несовместимой истории или достижении безопасного лимита
контекста.

## Идентичность сессии

`windows/get-kimi-session-marker.ps1` вычисляет стабильный SHA-256 marker из
нормализованного пути workspace. `windows/claw-kimi.cmd` добавляет его к имени
модели. Поэтому повторный запуск и `--resume` из той же папки попадают в ту же
запись `persistent_conversations`; случайный GUID больше не создаётся.

Если нужны две независимые линии работы в одной папке, задайте разные значения
`KIMI_CLAW_SESSION` вручную.

## Продолжение и автокомпактизация

Gateway сохраняет не текст переписки, а SHA-256 fingerprints входных сообщений.
При обычном продолжении совпадает весь старый префикс, и upstream получает только
новый хвост.

Claw-компактизация заменяет старый префикс системной сводкой, но сохраняет
последние сообщения без изменений. Gateway продолжает существующий `chat_id`,
если одновременно выполнены условия:

1. в первых четырёх API-сообщениях есть точный префикс штатной Claw-сводки;
   OpenAI-адаптер передаёт её как `user` после отдельного runtime `system`;
2. минимум два сохранённых сообщения точно совпадают с суффиксом ранее
   подтверждённой истории;
3. итоговая оценка не превышает лимиты сообщений и контекста.

Сводка повторно в Kimi не отправляется: upstream уже хранит старую историю.
Передаётся только новый user/tool delta. Если надёжного overlap нет, gateway
безопасно создаёт новый чат вместо ошибочного склеивания разных диалогов.

## Лимиты

Windows-конфигурация:

| Параметр | Значение | Назначение |
| --- | ---: | --- |
| `CLAUDE_CODE_AUTO_COMPACT_INPUT_TOKENS` | `200000` | ранняя компактизация Claw |
| `KIMI_MAX_PERSISTENT_CONTEXT_TOKENS` | `200000` | страховочная ротация gateway |
| `KIMI_MAX_PERSISTENT_MESSAGES` | `1000` | аварийный count-guard, не основной лимит |

Официальная конфигурация Kimi CLI для `kimi-for-coding` указывает окно `262144`
и резерв `50000`: <https://github.com/MoonshotAI/kimi-cli/blob/main/docs/en/configuration/config-files.md>.
Порог 200000 оставляет около 62144 токенов до максимума и не пытается работать
на самой границе окна.

## Почему раньше появлялось много чатов

Были две независимые причины:

1. launcher создавал случайный session GUID при каждом запуске;
2. даже со стабильным marker gateway ротировал чат после 100 сообщений и ещё
   раз после переписывания истории при автокомпактизации.

Стабильный marker устраняет первую причину. Лимит 1000 и overlap-распознавание
устраняют вторую, сохраняя контекстный предохранитель.

## Agent off / Agent on и инструменты

- `/agent off` — Kimi сама решает, вызывать ли инструмент.
- `/agent on` — в текущем turn обязателен реальный tool call.

Оба режима получают полный актуальный registry инструментов и одинаковые права
процесса. Режим меняет обязательность вызова, а не доступность инструментов.
Архивная сводка не является источником сведений о доступных инструментах.

## Проверка после изменений

1. `python -m unittest discover -s tests -v`
2. открыть `/health` и проверить:
   - `persistent_chat: true`;
   - `persistent_messages_limit: 1000`;
   - `persistent_context_tokens_limit: 200000`.
3. Сделать продолжение одной Claw-сессии и убедиться, что в stderr есть
   `continued across Claw compaction`, а между соседними запросами нет нового
   `POST https://www.kimi.com/api/chat`.
4. Новый workspace обязан создать отдельный upstream-чат; это ожидаемая
   изоляция, а не ошибка.

`persistent_chat_count` показывает количество локальных ключей, но сам по себе
не доказывает отсутствие upstream-ротаций. Для диагностики всегда сопоставляйте
его с `POST /api/chat` в gateway stderr.
